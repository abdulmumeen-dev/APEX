# APEX — product outcomes

APEX is an **open-source, standalone, local-first agent workstation** with its own agent engine. The local product runs on the user's computer without an APEX-hosted service, another agent, or a managed database. Users may connect a cloud model API directly with their own key, or run a local model such as Ollama without an API key. Cloud model calls require internet and send selected prompts/context to that provider; local Ollama can work offline after installation and model download. The broader goal draws inspiration from Manus/Desktop/Cue, Kimi Work/Desktop, Hermes Desktop, OpenClaw, Meta Muse, OpenAI Dots, Grok agents, and other systems without claiming literal parity or undocumented integrations.

## Product outcomes

- [ ] **Product, documentation, and public source foundation** — Name the project APEX; use the owner-selected MIT License; document real architecture, local setup, supported capabilities, limitations, security policy, contributions, research, and roadmap. Create the requested public GitHub repository through the supported user-controlled handoff and complete the publication visibility there. Do not represent the private/Manus remote or Preview as a public GitHub release.

- [x] **Standalone local runtime and optional cloud model APIs** — APEX's local edition must run on the user's computer without Manus login, an APEX-hosted backend, another agent, or a managed cloud database. It must support a local Ollama model without an API key and allow the user to configure a cloud model API directly with that provider's API key. The user chooses the provider and endpoint; APEX does not silently select a hosted provider. Cloud inference requires internet and sends the selected prompt/context to the chosen provider; local Ollama inference can remain on the computer after Ollama and model installation. Clearly disclose the selected execution/data path.

- [ ] **Downloadable desktop application** — Provide a real installable APEX Desktop application, not only a CLI, hosted Preview, or localhost page. The desktop shell must launch APEX's local runtime, let the user choose a local workspace with a native folder chooser, and display the local task/dashboard experience. Provide reproducible Windows, macOS, and Linux package targets; publish signed/checksummed and, where required, notarized downloads only after those release controls are actually configured. Keep the underlying local CLI and dashboard available as complementary surfaces. Current evidence: Electron shell, native project chooser, and OS build definitions are present; a Linux x64 AppImage was generated, but has not been launched/tested in the sandbox or signed/published. Windows/macOS artifacts have not been built here.

- [x] **Distinct desktop work areas** — Organize the local desktop into separate, named sections for **Agent**, **Code & Files**, **Create Game**, **Create Video**, **Browser & Computer**, **Research**, **Automations**, **Skills**, **Integrations**, **Models**, **Run History**, **Memory & Knowledge**, and **Assets & Files**. Label every section **Available**, **Limited**, **CLI only**, **Hosted only**, or **Planned** as appropriate. Available sections must invoke real APEX behavior; planned sections must clearly say they are not implemented, state what is available today and what remains, and must not fake execution, integrations, asset generation, video creation, or game previews.

- [x] **Local daemon and dashboard** — Provide `apex dashboard` as a single-user service bound only to `127.0.0.1`, serving the dashboard and local API without OAuth, hosted APEX, MySQL, CORS exposure, or any public/LAN listener. The daemon uses the project root selected at startup (default current directory); browser requests cannot choose arbitrary roots. Display the actual root and model. Provide model configuration/test, task submission, current run status and trace, and exact per-file-write approval/rejection. Shell execution from the browser stays disabled. Validate Host and same-origin requests, limit request sizes, and explain this loopback service is not an OS sandbox. A hosted Preview must clearly report that the local daemon is unavailable rather than pretending to reach the owner's computer. Verified by local route/API smoke requests and tests for host/origin rejection, key encryption, local tool calls, and write approval.

- [x] **Local execution engine shared by CLI and desktop/dashboard** — Refactor the current local CLI loop into one callable engine used by both the CLI and local daemon/desktop. The same local model selection, project file boundaries, Skills instructions, reasoning/tool limits, run events, and write-approval rules must apply across these local surfaces. Keep hosted mode's existing server/database loop a separate explicit deployment until a deliberate shared-kernel refactor is complete; do not claim universal runtime parity yet. Local dashboard integration tests and the CLI suite exercise the exported local loop.

- [x] **Local state and credential protection** — Store local model configuration and run traces beneath the user's APEX config/data directory with owner-only directory/file permissions and atomic writes. Never return an API key to the browser/desktop renderer after saving it. Encrypt a saved cloud API key with AES-256-GCM under a generated local 32-byte key stored owner-only. Preserve no-key Ollama setup. Local API requests and error traces must not log or expose credential material. The local dashboard tests verify ciphertext storage and non-return of the key.

- [x] **Broad capability coverage and gap register** — Track what APEX has, what is partial, and what remains to build in `docs/capability-gap-register.md`. Cover desktop/workspace tabs, CLI/TUI, local files/terminal/coding, browser/computer operation, research, documents and multimodal inputs, cloud/local models, integrations/MCP/extensions/assets, memory/context, durable automation, approvals/effect ledger, isolation/security, release/update, reliability/observability, and beneficial specialist Skills. Show a feature as available only after its actual implementation; keep competitor references distinct from APEX product claims.

- [x] **CLI agent** — Provide real remote run, persistent chat, status, history, Skills, Plugin listing, token login/logout, and local-project modes. Remote mode must call the same run engine and trace as the hosted dashboard. Local mode must scope file operations to `--cwd`, exclude common secrets/dependencies, reject symlinks, require per-write confirmation unless explicitly bypassed, keep shell opt-in, and confirm each exact command.

- [ ] **Local-first onboarding without provider keys** — A user must be able to use APEX's local CLI and desktop/dashboard with Ollama without an APEX server account, hosted-model account, or provider API key. `apex setup` must detect Ollama or direct the user to install it, find or offer a tool-capable local model, disclose the download size, ask before downloading, save local configuration with user-only permissions, and explain when setup is complete. Current CLI behavior offers `qwen3.5:4b` only after disclosing its approximate 3.3–4.0 GB download and asking confirmation; desktop onboarding remains to be completed.

- [ ] **Cloud provider compatibility and truthful model checks** — Allow user-configured cloud endpoints only when the selected API and model are supported by the adapter. Do not equate a successful `/models` request with working tool calls. Add a provider/model conformance path for model listing, auth, ordinary completion, tool request/response, and error behavior. Record current documented candidates and caveats in `docs/cloud-provider-compatibility-review.md`; no vendor credentialed live conformance has been performed for every provider in that report.

- [ ] **Web dashboard and API surfaces** — Keep the authenticated hosted dashboard and personal-token API usable as optional first-party hosted surfaces of the hosted run engine; expose truthful provider, CLI token, Skill, Plugin, workflow, history, memory, workspace, and security state. Keep the standalone local dashboard/API independent of hosted OAuth/MySQL.

- [ ] **APEX's own loop, tools, and private context** — Persist user tasks, messages, real model calls, bounded tool results, session-owned memory, versioned workspace files, run states, and actual execution traces. Support owner-scoped inspection/deletion in hosted mode and inspectable local run records in local mode; keep prompt-injected external/tool content untrusted.

- [ ] **User-owned Skills** — Support versioned instruction bundles that affect the actual APEX prompt only when enabled. Limit simultaneous Skills and forbid Skills from silently adding tools or permissions. Include a mock-interview practice Skill that helps users express their own real experience. Live assistance must be disclosed/permitted; no covert answer feed, candidate impersonation, or fabricated credentials.

- [ ] **Bounded API Plugins** — Support user-configured, fixed-path read-only JSON GET endpoints. Live-test before enabling, encrypt API keys, enforce strict query/response limits, block private networks/redirects by default, and ask for separate per-run permission before external data egress.

- [ ] **Optional agent bridges** — Keep APEX capable without external agents, but allow verified peers to be connected and delegated to under explicit run consent, data-boundary notice, scoped credentials, and durable trace. A generic APEX Bridge v1 is not a claim of native connection to Grok Build, Cue, OpenClaw, Hermes, Kimi Work, Meta Muse, or OpenAI Dots. Keep Meta Muse and OpenAI Dots distinct; build a named adapter only if its public control protocol is documented and actually implemented.

- [ ] **Automations** — Save validated drafts and permit real manual Run once execution. Do not label schedule/webhook triggers active until a restart-safe authenticated worker has been configured and verified. Add durable idempotency, retry/backoff, cancellation, approval waits, missed-run policy, and event receipts before unattended use.

- [ ] **Human approvals and effect ledger** — Persist actual approval requests, exact action arguments, decisions, expiry, and pause/resume. Keep attempted, confirmed, and externally verified effects distinct. Do not claim a consequential side effect succeeded from model text alone.

- [ ] **Security and run isolation** — Provide truthful safety controls and threat model. Treat UI and CLI confirmation as guardrails, not a sandbox. Implement and test an OS/container-isolated runner with resource, filesystem, secret, and network controls before enabling untrusted-code execution or public multi-user access.

- [x] **Evidence-backed product strategy** — Use `docs/agent-landscape.md`, `docs/desktop-agent-review.md`, `docs/cloud-provider-compatibility-review.md`, `docs/capability-gap-register.md`, and the commissioned `docs/product-ideas/` reports to prioritize portable context, explicit policy/effects, reliable automation, useful local workflows, desktop/browser coverage, extensions, privacy, and beneficial interview coaching. Preserve citations and distinguish evidence from APEX recommendations.

## Deployment boundary

The hosted Preview uses Manus OAuth and managed MySQL. The local daemon, shared CLI/dashboard loop, Electron shell, work-area navigation, and multi-OS build workflow exist in source. A Linux AppImage was generated and smoke-opened under Xvfb through the native workspace chooser and main window; it is unsigned, not yet tested on a real user machine, and not published. Windows/macOS packages remain to be built and platform-validated. Local Ollama use needs no provider key, but the user must install Ollama; a cloud model API uses the selected provider's key and network. API-key storage for hosted profiles requires the operator's 32-byte `APEX_ENCRYPTION_KEY`; local key storage uses a generated local encryption key. A cloud Preview cannot access the user's desktop `localhost`. APEX local CLI's optional shell runs with the OS user's permissions and is not sandboxed. Do not advertise production-grade isolation, unattended consequential automation, or feature parity before the relevant controls are delivered.
