# APEX product opportunity: portable skills, plugins, and tool standards

APEX can differentiate as a **portable capability runtime**, not merely another agent UI. The user problem is that reusable agent behavior currently spans several partially overlapping conventions: a skill may be Markdown instructions, a plugin may be executable code, and a connector may be an MCP server, OpenAPI endpoint, CLI, or another agent. Users need to move a capability between a local APEX install, a daemon/API, and a dashboard without losing its dependencies, permissions, provenance, or audit trail. They also need to know what a capability can do **before** it is placed in model context or allowed to execute.

## Documented evidence

1. **A portable skill format exists, but it is intentionally narrow.** The Agent Skills specification defines a directory with `SKILL.md`, optional scripts/references/assets, YAML metadata, compatibility notes, and experimental `allowed-tools`; it recommends progressive disclosure so metadata is loaded first and resources only when needed. The body has few format restrictions, while supported executable languages depend on the implementation. [1] This is a useful interchange layer for instructions and references, but not a complete plugin contract for executable tools, secrets, network access, isolation, or lifecycle policy.

2. **MCP standardizes tool/context connection, while A2A standardizes agent-to-agent task exchange.** MCP defines hosts, clients, and servers over JSON-RPC and exposes resources, prompts, and tools; its own specification says tools represent arbitrary code execution and that hosts should obtain explicit consent. [2] MCP’s Skills extension now defines discovery and retrieval of Agent Skills through Resources, including a complete file manifest with SHA-256 digests and cache metadata; it also states that implementation support is still being built. [3] Google’s A2A announcement (April 9, 2025) positions A2A as complementary to MCP: A2A handles opaque-agent collaboration, capability discovery via Agent Cards, long-running tasks, artifacts, and status updates, while MCP supplies tools and context. [4]

3. **The ecosystem has an explicit packaging gap.** The MCP Skills working-group charter says installable bundles combining skills, servers, subagents, and configuration are out of scope for that extension and belong to a broader packaging effort. [5] This is a direct opening for APEX: provide a signed, portable bundle format that composes an instruction skill with executable tools, connectors, model requirements, policies, tests, and rollback metadata.

4. **Plugin/skill supply-chain risk is documented as a first-order problem.** OWASP’s Agentic Skills Top 10 AST02 describes skill registries with weak provenance, dependency confusion, maintainer takeover, repository-config execution, and “no code signing, no security review, no sandbox by default” in an example marketplace; it recommends signed canonical digests, transparency logs, pinned recursive dependencies, private mirrors/allowlists, and revocation. [6] Trail of Bits independently documented “line jumping” (April 21, 2025): a malicious MCP server can inject instructions through tool descriptions as soon as a client connects, before a tool is invoked, defeating a simplistic human-approval checkpoint. [7]

5. **Approval UI is not the same thing as OS/container isolation.** The NSA’s *Model Context Protocol (MCP): Security Design Considerations* (May 2026) notes that MCP does not enforce security principles at the protocol level, that access control/RBAC, token lifecycle, task isolation, and comprehensive audit logging are often left to implementers, and that already-trusted servers can change behavior without a new approval. [8] NIST SP 800-190 (September 2017) describes containers as portable packaging plus OS virtualization, but treats image, registry, runtime, host, and orchestration security as separate concerns. [9] APEX should therefore make approvals a policy decision and use an actual restricted runner for untrusted code; a click on “Allow” must never be presented as proof of containment.

6. **Interview assistance has a legitimate accessibility and coaching use case, but covert answer-feeding is a different product.** U.S. DOJ guidance says hiring technologies can unlawfully screen out qualified people with disabilities and that employers must provide reasonable accommodations during hiring; it recommends explaining the technology/evaluation and having clear accommodation procedures. [10] This supports disclosed assistive functions such as captions, transcription, alternative input, extra processing time, or a user-requested communication aid. It does not support secretly supplying answers in a live assessment. APEX should explicitly distinguish (a) mock interview practice and feedback, (b) disclosed accessibility support agreed with the interviewer, and (c) covert real-time answer generation that misrepresents the candidate’s independent performance. The third creates integrity, privacy, consent, employment-policy, and reputational risks and should not be a packaged APEX skill.

## Actionable APEX designs

1. **APEX Capability Bundle (portable manifest).** Define a versioned `apex.yaml`/JSON manifest that wraps an Agent Skills-compatible `SKILL.md` with: executable entry points; MCP/A2A/OpenAPI/CLI adapters; model and runtime compatibility; input/output JSON Schemas; required filesystem paths; network destinations; secret names (never secret values); data-retention class; side effects; license; and a deterministic bundle digest. Keep instructions, tools, and policy as separate signed sections so a text-only skill cannot silently acquire code or credentials.

2. **Capability-based permission broker.** Require every tool call to pass a runtime policy that grants narrowly scoped capabilities such as `fs.read:/workspace`, `net.connect:api.example`, or `calendar.write`. Show the requested scope, data classification, destination, and irreversible effect in CLI/TUI/dashboard. Cache approval only for the exact server identity, bundle digest, tool schema, and scope; invalidate it on any change. This operationalizes MCP’s consent principle without treating consent as a sandbox.

3. **Trust, provenance, and rollback plane.** Ship a registry/lockfile workflow with publisher keys, signed canonical manifests, recursive dependency hashes, transparency-log entries, vulnerability/status metadata, private mirrors, and revocation. On update, display a semantic diff of instructions, tool descriptions, permissions, dependencies, and container image digest; default to pinning rather than “latest.” Support offline verification for self-hosters.

4. **Real isolation profiles.** Run executable plugins in an ephemeral, rootless OCI-compatible container or stronger VM boundary, with read-only base image, isolated workspace, dropped Linux capabilities, seccomp/AppArmor or equivalent, CPU/memory/time quotas, blocked-by-default egress, explicit domain allowlists, and redacted secret injection. Offer a “trusted local process” profile only as an explicit risk choice. OCI provides portable image/runtime/distribution specifications, while NIST’s container guidance makes clear that the runtime and host still need hardening. [9]

5. **Progressive discovery with integrity checks.** Load only small metadata at startup. Fetch full instructions, references, and tool schemas on activation; verify the manifest’s digest before model exposure; quarantine suspicious descriptions and control characters; and require re-approval when content or capabilities change. This follows Agent Skills’ progressive-disclosure design [1] and MCP Skills’ manifest/digest model [3], while addressing the pre-invocation injection documented by Trail of Bits [7].

6. **Protocol-neutral adapter and conformance kit.** Make APEX’s internal contract independent of any provider: adapters for MCP tools/resources/prompts, A2A Agent Cards/tasks, OpenAPI operations, local functions, and CLI commands should normalize schemas, streaming, cancellation, retries, idempotency, authentication, and error semantics. Publish a test suite and golden traces so a skill can be validated against the same behavior in CLI/TUI, daemon/API, and dashboard. Treat A2A as optional delegation, not as permission to forward the user’s whole memory or credentials.

7. **Auditable execution ledger and circuit breakers.** Record immutable, privacy-aware events for discovery, approval, policy evaluation, model-visible content, tool arguments/results, subprocess/container identity, network destinations, and redactions. Add per-run budgets, maximum delegation depth, cancellation, replayable dry-run mode, and a kill switch that revokes a bundle or connector. Make the ledger exportable for self-hosted incident response; keep raw sensitive content off by default.

8. **Interview-safe skills.** Package a mock-interviewer skill that uses the candidate’s own résumé and job description to generate practice questions, rubric-based feedback, and a “show your work” rehearsal. Separately provide disclosed accessibility helpers—local captions/transcription, keyboard/alternative-input support, adjustable pacing, and a consent script the candidate can share with the interviewer. Do not ship covert answer-feeding, hidden screen scraping, impersonation, or stealth audio capture. A user can still use APEX to research an employer, rehearse truthful examples, and organize accommodations without misrepresenting independent performance or sending interview audio to an undisclosed provider.

## Cautions and open decisions

- **Do not claim protocol portability equals security.** MCP and A2A improve interoperability, but authentication, authorization, isolation, token lifecycle, and audit semantics remain implementation responsibilities. [2] [4] [8]
- **Do not rely on a green scanner or approval dialog as proof of safety.** Tool descriptions, referenced files, nested dependencies, update drift, and runtime behavior can change; combine provenance, least privilege, isolation, monitoring, and revocation. [6] [7]
- **Self-hosting shifts operational burden to the user.** APEX should ship secure defaults, threat-model templates, upgrade/revocation guidance, and a clear warning when a connector runs outside the sandbox or receives long-lived credentials.
- **Minimize model and connector data exposure.** Redact secrets and unrelated memory, use per-run identities, prefer local processing for interview audio/accessibility features, and make retention/deletion visible. NIST’s AI RMF is voluntary risk-management guidance, not a legal safe harbor. [11]
- **Interview policy is contextual.** Mock coaching and agreed accommodations are user-beneficial; covert answer-feeding can violate employer rules, undermine valid assessment, expose private conversation data, and harm both candidate and employer. APEX should refuse to automate the covert mode while offering a clear route to disclosed support.
- **Evidence limits.** The sources document protocol design, security failure modes, and accommodation obligations. They do not establish market prevalence or prove that any particular APEX design will prevent all attacks; validate with threat modeling, conformance tests, and usability/security evaluations.
