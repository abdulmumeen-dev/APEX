# APEX opportunity 07: model choice, privacy, and cost controls

APEX’s differentiator should not be “one model that does everything.” It should be a **policy-governed runtime that makes model, data, tool, and spend decisions visible and enforceable**. A user bringing a hosted API, OpenAI-compatible server, or local model currently has to infer privacy and cost behavior from provider terms, endpoint defaults, model capabilities, and their own connectors. In an autonomous runtime, this uncertainty compounds: prompts can include memory, files, connector results, plugin code, delegated-agent context, and automation history.

## The user problem, and what the evidence establishes

**User problem.** Users need to answer four operational questions before an agent run: *What data leaves this machine? Which model/provider receives it? How long can each party retain it? What is the worst-case cost if the agent retries, delegates, uses tools, or runs unattended?* Existing model APIs expose pieces of this answer, but not a common contract. The same “private” workflow can still leak through a connector, cache, batch queue, telemetry path, or a tool with a different retention policy.

The evidence below is documented fact, not a claim about market prevalence:

1. **Hosted API privacy is endpoint- and feature-specific.** OpenAI states that API data is not used to train models unless the customer opts in, but its default abuse-monitoring logs may include prompts and responses for up to 30 days. Zero Data Retention is an eligibility-controlled setting, and some features can still retain application state; remote MCP servers and other third parties follow their own policies.[1] Anthropic similarly documents feature-specific retention, says conversation content is not retained by default except for designated “Covered Models” requiring 30-day retention, and says its ZDR arrangement does not cover several interfaces, managed agents, or third-party integrations.[2] **Implication:** a provider name or “API” label is not enough for APEX to make a privacy promise.

2. **Local inference can materially reduce provider exposure, but does not make the whole run private by itself.** Ollama’s March 2026 privacy policy says locally processed prompts and responses are not collected, stored, transmitted, or accessible to Ollama, while cloud-hosted models are processed transiently and device/account metadata is still collected.[3] APEX still has to account for its own dashboard, logs, memory, connectors, model downloads, plugin network calls, and any fallback from local to hosted inference.

3. **Agent context creates a security problem beyond model selection.** NIST’s *Generative AI Profile* (published July 26, 2024) describes indirect prompt injection through retrieved websites or files and notes demonstrations in which attackers stole proprietary data or ran code remotely. It recommends privacy red-teaming for disclosure of confidential, personal, proprietary, biometric, location, and other sensitive information.[4] OWASP’s LLM01:2025 says prompt injection can disclose sensitive information, obtain unauthorized function access, execute commands in connected systems, and manipulate decisions; it also says there is no foolproof prevention and recommends least privilege, segregating untrusted content, human approval for high-risk actions, and adversarial testing.[5]

4. **A click-through approval is not an isolation boundary.** NIST SP 800-190 (September 2017) says containers share a host kernel and therefore provide a less concrete boundary than VMs; it warns that privileged containers can effectively act as part of the host OS and that unbounded network access can expose other resources.[6] Docker’s security documentation likewise warns that a Docker daemon normally has root privileges, that host filesystem sharing can let a container alter the host, and that default capabilities/mounts may provide incomplete isolation.[7] **Implication:** APEX’s “Approve” button can establish user intent, but it cannot substitute for rootless execution, capability reduction, filesystem/network policy, and (for high-risk workloads) a VM or microVM boundary.

5. **Cost controls are technically available but fragmented across providers.** OpenAI’s pricing documentation exposes distinct standard, cached-input, and batch prices; its current table shows batch prices at roughly half of standard prices for many models.[8] Anthropic documents a Message Batches API with a 50% discount, asynchronous completion, a 24-hour processing window, and server-side retention of batch inputs/results for up to 29 days.[9] Anthropic’s prompt caching uses a five-minute default TTL and an optional one-hour TTL, with separate cache-write and cache-read prices.[10] These mechanisms can reduce spend, but they also create retention, freshness, and latency tradeoffs that a single APEX “cost estimate” must represent.

6. **Cost-aware routing is a plausible design direction, not a guaranteed quality win.** A 2025 preprint evaluates a cost-spectrum router on several benchmarks and reports improved cost/quality tradeoffs against the baselines it tested, including out-of-distribution prompts.[11] That is evidence that routing can be studied and measured; it is not evidence that one router generalizes to APEX users, models, languages, or agent tasks. APEX should require workload-specific evaluation and expose uncertainty rather than silently routing based on an unvalidated score.

## Model choice and privacy: actionable APEX design

1. **Create a signed “model/provider contract.”** Represent every model endpoint with machine-readable fields: operator and region; model/version; local versus remote execution; training-use statement; abuse-log and application-state retention; ZDR availability and eligibility; cache and batch behavior; supported modalities; subprocess/tool permissions; price schedule; rate limits; and last-verified timestamp. Treat unknown fields as unknown, not private or free. At run planning time, show a plain-language route such as “resume text → local model; calendar metadata → hosted model, provider retention up to 30 days; website content → untrusted.”

2. **Add sensitivity-aware routing with no silent fallback.** Label inputs and memory records (for example: public, personal, confidential, regulated, secret) and let policy map labels to approved model classes. For confidential or regulated data, default to local/offline inference or an explicitly approved endpoint. Redact or tokenize identifiers before routing where possible. If the local model fails, pause and ask permission before sending the data to a hosted fallback. A dry-run should list the exact fields, connectors, and model endpoints that would receive data.

3. **Separate “model quality,” “privacy posture,” and “tool authority.”** A large model is not automatically safer, and a local model is not automatically reliable. APEX’s model picker should show three independent scores: task-quality evidence from the user’s benchmark; privacy/retention posture from the provider contract; and authority required by the task. Do not let a high-quality model silently gain broader filesystem, browser, email, or delegation access.

4. **Build privacy-preserving memory and connector controls.** Store sensitivity and provenance with each memory item; provide per-item TTL, delete/export, and “never send to hosted models” flags. Keep raw prompts and connector payloads out of ordinary logs; log hashes, policy decisions, endpoint IDs, token counts, and redaction events instead. Make each connector declare what it can transmit and to whom. A remote MCP/plugin should be treated as a separate processor with a separate retention policy, not as part of APEX’s privacy boundary.

## Cost controls that users can understand

5. **Implement a budget ledger and hard stop.** Before a run, estimate input/output tokens, tool calls, retries, delegated calls, cache writes/reads, batch fees, and local compute assumptions. During execution, meter actual provider usage and show estimated versus billed cost. Support budgets at user, project, automation, and single-run levels; enforce hard ceilings, max iterations, max output tokens, concurrency limits, and a kill switch. An unattended automation must fail closed when a budget or provider price manifest is stale.

6. **Offer explicit quality/cost routing tiers.** Let users define policies such as “local first,” “cheapest model meeting benchmark threshold,” “premium model only for code review,” or “never exceed $0.25 per task.” Maintain a small per-workload evaluation set and periodically compare routes. Use cheap models for classification, extraction, and planning only when the user’s tests support it; escalate difficult or high-impact steps to a stronger model. Record the reason for every escalation and allow a user to replay a run with another route. APEX should present routing research as a tradeoff tool, not promise universal savings.

7. **Make caching and batching opt-in, observable, and privacy-aware.** Display cache TTL, cache key scope, what prefix is retained, and whether a batch stores inputs/results. Use caching only for stable, non-sensitive prefixes unless the user explicitly approves otherwise. Offer asynchronous batching for evaluations, indexing, and bulk summarization, but never use it for interactive or time-sensitive actions without clearly showing the latency and retention consequence.

8. **Define a real execution boundary for tools and plugins.** Keep UI approval for consent and auditability, but execute untrusted skills, plugin code, browser automation, and delegated agents in a rootless sandbox with read-only mounts by default, dropped capabilities, resource limits, no host socket, and deny-by-default egress. Use a VM/microVM or separate host for secrets, arbitrary code, or high-risk connectors. Require signed/version-pinned plugins and a secrets broker that gives short-lived, task-scoped credentials. This directly addresses the container limitations documented by NIST and Docker.[6][7]

## Interview assistance: beneficial alternatives and a boundary

APEX should support **mock coaching**: question banks, role-play, rubric-based feedback, STAR-story practice, coding rehearsal, accessibility-friendly pacing, and post-session reflection. It can support **disclosed accessibility assistance** when the applicant and employer agree on the accommodation, for example local speech-to-text, captions, an accessible interface, or extra time. DOJ guidance (May 12, 2022) says hiring technologies must not screen out qualified applicants with disabilities and that employers must provide reasonable accommodations; it recommends telling applicants what technology is used and providing a clear accommodation process.[12]

APEX should not market or optimize **covert live answer-feeding**. A published Jack Henry candidate policy permits AI to help craft resumes and permits assistive AI for a disability when communicated to the recruiter and approved, but strictly prohibits AI assistants or notetakers answering live interview questions.[13] University of Illinois guidance likewise requires notice, explanation, and written consent for AI analysis of video interviews and states that employment decisions must be made by a person.[14] Covert answer-feeding can misrepresent identity and ability, violate interview rules, expose the interviewer’s voice/video and confidential questions to an unapproved processor, and create an accessibility pretext that deprives the applicant of genuine informed consent.

A safe product boundary is an “Interview practice and disclosed assistance” mode: local-first processing; conspicuous status and transcript controls; no hidden overlays, synthetic voice, impersonation, or automatic submission; an employer-policy checklist; an exportable disclosure/audit record; and a one-click pause when a user asks for live answers. If an employer explicitly authorizes a live assistant, APEX should require the user to record that authorization and apply the employer’s stated data, model, and retention constraints. This is a product-integrity recommendation, not a claim that every jurisdiction or employer has the same rule.

## Cautions and confidence

- Provider retention, prices, model names, and ZDR eligibility change. Contracts must expire and be re-verified; “current” should always show a timestamp and source.
- Local inference reduces third-party model exposure but does not stop connector egress, malware, telemetry, insecure plugins, or a compromised host. Self-hosting shifts responsibility to patching, access control, backups, and runtime hardening.
- Prompt-injection defenses are layered risk reduction, not a proof of safety. Approval UX is not OS/container isolation.
- Routing results are workload-dependent. The cited routing study is a preprint with benchmark-specific results, not a general effectiveness experiment.
- Interview and recording rules vary by employer and jurisdiction. APEX should not provide legal advice or infer that disability accommodation permits undisclosed answer generation.

**Confidence: medium-high** for the documented provider, security, cost-feature, and accommodation facts; **medium** for the product recommendations because APEX’s final threat model, target users, and supported providers are not yet fixed.
