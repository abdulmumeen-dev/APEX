# APEX product opportunity: reliable long-running agent automations

**User problem.** People can prototype an agent in one process, but dependable automations that run for hours, days, or weeks must survive crashes, restarts, provider/API failures, human waiting, model changes, and partial tool execution. They also need bounded authority: a dashboard approval click is not equivalent to authorization or OS/container isolation. APEX can differentiate as a self-hostable, provider-neutral runtime that makes progress, state, approvals, side effects, and recovery inspectable and repeatable across its CLI/TUI, API/daemon, and dashboard.

## Documented evidence

1. **Long-running execution needs durable state and replay, not an in-memory loop.** Temporal defines workflow durability as having no imposed time limit and says its platform persists workflow state through failures and resumes from the latest state; replay uses recorded event history to resume progress. [1] LangGraph similarly says persistence is needed to resume after interruption or failure, while warning that in-memory checkpoints disappear on process restart and production needs a persistent checkpointer. [3] This is direct evidence for durable run records, resumable cursors, and explicit retention in APEX—not evidence that any particular engine guarantees correctness for arbitrary side effects.

2. **Retrying the whole agent is unsafe and can be wasteful.** Temporal documents that Activities retry by default with exponential backoff, while Workflows do not; it recommends retrying failed Activities rather than replaying an entire Workflow because whole-workflow retry can repeat unchanged logic and consume resources. [2] Google Cloud Workflows exposes separate default policies for idempotent and non-idempotent steps and cautions that the idempotent policy should only be used where repetition is safe. [10] AWS Step Functions provides per-state `Retry`/`Catch`, bounded attempts, backoff, jitter, and fallback handling. [9] The product implication is to model every tool call as a typed, retry-aware action with an idempotency class and a visible failure policy.

3. **Human approval is a first-class pause/resume state, but approval must be bound to the exact action.** LangGraph’s documented interrupt pattern persists graph state and waits indefinitely until resumed, enabling approval, review/edit, and tool-call interruption. [4] OWASP’s Agent Security Cheat Sheet goes further: a `user_confirmed` flag is insufficient; the execution component must verify actor, exact tool call, parameters, expiry, and one-time consumption atomically, with unknown tools failing closed. [6] APEX should treat approval as a signed, expiring capability checked outside the model context—not as a UI event.

4. **Agent inputs and memories are hostile data paths.** OWASP defines direct and indirect prompt injection and lists impacts including sensitive-information disclosure, unauthorized function access, arbitrary commands in connected systems, and manipulation of critical decisions; it says there is no foolproof prevention and recommends least privilege, external-content separation, human approval for high-risk actions, and adversarial testing. [5] Independent Unit 42 research (published March 3, 2026) reports in-the-wild web-based indirect prompt-injection detections with observed intents including data destruction, unauthorized transactions, sensitive-information leakage, and system-prompt leakage, while also distinguishing theoretical severity from the more limited real-world cases observed so far. [11] A 2025 survey of LLM-agent workflow threats catalogs attacks across inputs, tools/protocols, privacy, and agent-to-agent communication, recommending provenance, authentication, ACLs, replay protection, and per-agent validation. [12]

5. **“Sandboxed” and “approved” are different security claims.** NIST SP 800-190 (published September 2017) describes containers as operating-system virtualization and packaging, and documents container security concerns and recommendations. [8] Docker’s rootless documentation says rootless mode runs both daemon and containers without root privileges in a user namespace to mitigate daemon/runtime vulnerabilities; it does not claim that a container is a universal host-isolation guarantee. [7] Therefore APEX should expose security profiles and capabilities precisely: UI approval controls authorization policy; a sandbox profile controls process/filesystem/network exposure; neither substitutes for the other.

6. **Interview use requires an integrity and accessibility boundary.** ADA.gov guidance (May 12, 2022) says hiring technologies can unlawfully screen out qualified people with disabilities, requires reasonable accommodations during hiring, and gives accessible interview software or assistive equipment as examples. [13] That supports disclosed, user-controlled accessibility assistance. It does not support covert answer-feeding that misrepresents the candidate’s own performance. APEX should not ship or market a hidden live interview answer agent; it can instead support mock interviews, preparation, disclosed transcription/captioning, and employer-approved accommodations. No prevalence or effectiveness claim about covert tools is inferred here.

## Actionable APEX ideas

1. **Durable run ledger and event-sourced checkpoints.** Persist immutable run events, tool-call intents/results, model/provider metadata, approvals, timers, and checkpoint snapshots in a local database selected by the operator. Give every run a stable ID and let CLI/TUI, API, and dashboard attach to the same cursor. Add retention, export, encryption-at-rest hooks, and a “resume from checkpoint / fork as new run” operation.

2. **Step-level recovery planner.** Represent automation as typed steps with timeout, cancellation, retry predicate, max attempts, exponential backoff/jitter, and a permanent-failure path. Require each side-effecting connector to declare `idempotent`, `deduplicated`, or `non-idempotent`; require an idempotency key or explicit operator confirmation before retrying non-idempotent work. Never silently restart the whole plan after an ambiguous tool timeout.

3. **Action journal and reconciliation.** Before execution, record normalized tool name, target, parameters hash, actor, capability, and idempotency key. After a timeout, enter `unknown outcome` and offer connector-specific status lookup or human reconciliation instead of blindly repeating. Make external actions (email, tickets, payments, file writes) show “planned / dispatched / acknowledged / reconciled” states.

4. **Approval broker outside the model.** Define risk classes and deny-by-default policy for unknown tools. Render a human-readable preview plus exact parameters, affected resources, data egress, and expiry. Bind approval to actor, run, tool, normalized parameters, policy version, and one-time nonce; atomically consume it in the daemon immediately before execution. Record both approval and rejection in the audit trail.

5. **Capability-based connector and sandbox profiles.** Give each skill/plugin a manifest declaring filesystem paths, network destinations, secrets, subprocess needs, and read/write scope. Enforce it in the execution layer, not in a prompt. Offer profiles such as read-only, workspace-write, network-denied, and isolated worker/microVM (where available), with a clear warning that rootless containers are defense-in-depth rather than a universal isolation proof. Add secret redaction and per-run egress logs.

6. **Untrusted-content quarantine and provenance.** Label web pages, emails, documents, tool responses, and retrieved memories as data, not instructions. Keep source metadata and hashes; pass untrusted content through a separate extraction/validation step; prevent it from changing tool permissions or system policy. Add an adversarial “prompt-injection test mode” for skills/connectors and a kill switch that pauses all new side effects while preserving state.

7. **Operator-grade observability and repair.** Provide a timeline with current state, waiting reason, next timer, retry count, cost/token estimates, model/provider, tool permissions, and last successful checkpoint. Support pause, cancel, resume, replay-for-debug, and fork-with-edits. Emit structured logs and OpenTelemetry-compatible spans, but make sensitive payload logging opt-in with redaction.

8. **Beneficial interview-adjacent workflows only.** Ship a mock-interview skill that asks questions, times answers, gives feedback, and helps the user practice from their own experience. Offer disclosed live captions, transcription, translation, note-taking, or communication assistance behind an explicit “employer-approved accommodation” mode that does not generate deceptive answers. Block or refuse covert answer-feeding, impersonation, hidden overlays, and fabricated experience; explain the boundary and redirect to preparation or accessibility support. Minimize retention of voice, transcripts, resumes, and employer data, with local-only processing where possible.

## Cautions and open questions

- Durable replay does not make arbitrary external side effects exactly once. APEX must surface at-least-once/unknown-outcome semantics and require connector-specific idempotency or reconciliation.
- “Human in the loop” can become rubber-stamping. Approval previews, risk-based escalation, short expiries, independent policy checks, and auditability matter more than a confirmation button.
- Prompt-injection defenses are layered mitigations, not proof of prevention. Treat the model as untrusted with respect to authorization; test indirect injections in webpages, files, emails, memory, plugin metadata, and delegated-agent messages.
- Self-hosting shifts responsibility to the operator for OS patching, Docker/container configuration, database encryption, backup security, connector tokens, and network egress. Document the difference between UI policy, process sandbox, container isolation, and stronger VM/microVM isolation.
- Interview assistance can create privacy, employment-law, and assessment-integrity risks. Accessibility support should be disclosed and employer-approved; a covert answer agent misrepresents competence and may expose confidential interview content. APEX should not optimize for evasion or concealment.
- Validate designs with fault-injection tests (crash during each state, duplicate webhook, delayed approval, provider outage, partial connector success) and security tests. These tests establish behavior for tested scenarios, not broad claims of reliability or market prevalence.
