# APEX product opportunity: Accessible multi-surface agent UX

## User problem

APEX’s single runtime will be exposed through a CLI/TUI, API/daemon, and dashboard, but users do not experience those surfaces as equivalent today. Screen-reader users can encounter unstructured terminal output, redraw-heavy prompts, spinners, color-only cues, and inaccessible web widgets. A user who starts a long-running task in one surface may also lack a reliable, understandable way to inspect status, approve an action, interrupt it, or resume it from another surface. The product opportunity is not “make the dashboard accessible” in isolation: it is to make **the runtime’s state, controls, permissions, and results semantically portable across surfaces**.

This is especially valuable for users with blindness or low vision, motor or cognitive disabilities, people who need keyboard-only or speech interaction, and users working in constrained environments. It also improves ordinary reliability: line-oriented output, durable task state, explicit progress, and exact approvals are useful for automation and debugging even when no assistive technology is present.

## What is documented

1. **CLIs are not automatically accessible because they are text.** A 2021 CHI study of 12 developers using screen readers found that the most important issue was that CLIs are “unstructured text interfaces,” and reported a distinct set of accessibility problems rather than assuming text alone solves them. [1]

2. **Real terminal implementations have concrete failure modes.** In a May 2, 2025 engineering report, GitHub described screen-reader difficulty with non-alphanumeric visual cues and constant screen redraws. It replaced a redraw-based spinner with static textual progress, addressed contrast and customizable colors, and noted that there is no equivalent comprehensive accessibility standard for terminals. [2]

3. **The web surface has testable requirements that map directly to agent UX.** WCAG 2.2 (republished December 12, 2024) adds or emphasizes focus not obscured, focus appearance, dragging alternatives, target size, consistent help, redundant entry, and accessible authentication. Its Status Messages criterion requires updates such as progress, waiting, success, and errors to be programmatically determinable without taking focus. [3] W3C’s WCAG2ICT guidance explicitly covers text/command-line/terminal applications and applies concepts such as no keyboard traps, labels, and visible focus to non-web software. [4]

4. **An agent’s approval dialog is not a complete security control.** OWASP’s LLM01:2025 guidance says direct and indirect prompt injection can cause sensitive-data disclosure, unauthorized function access, arbitrary commands in connected systems, and manipulation of critical decisions. It recommends least privilege, separating untrusted external content, adversarial testing, and human approval for high-risk actions, while warning that foolproof prevention is unclear. [5] OWASP’s agent-security guidance adds an important implementation detail: a `user_confirmed` flag is insufficient; authorization must be checked outside the agent and bound atomically to the current actor, exact tool call, normalized parameters, expiry, and replay protection. [6]

5. **Containerization is isolation infrastructure, not a promise of a safe sandbox.** NIST SP 800-190 (September 2017) describes container security as a set of concerns involving images, registries, the host OS, and the runtime. Docker’s security documentation explains that namespaces and cgroups help isolate processes and limit resource exhaustion, but also says default capabilities and mounts can provide incomplete isolation, especially with kernel vulnerabilities or unsafe configuration. [7] [8]

6. **Accessibility support in hiring is different from impersonating a candidate.** DOJ guidance published May 12, 2022 says the ADA applies to hiring technologies, employers must avoid disability discrimination, and reasonable accommodations can include assistive equipment or an accessible version of an online interview program. It gives a blind applicant using a screen reader as an example and recommends telling applicants what technology is used, how they will be evaluated, and how to request accommodation. [9] This supports disclosed accessibility assistance; it does not support covert answer generation.

## Actionable APEX product designs

1. **Define one accessibility-aware event model for the shared runtime.** Every task event should carry a stable task/run ID, sequence number, timestamp, human-readable summary, machine-readable type (`started`, `progress`, `approval_required`, `tool_result`, `error`, `completed`), severity, provenance, sensitivity, and available actions. The CLI/TUI, API, and dashboard should be renderers of this model, not three independent interpretations. Expose JSON/JSONL and a versioned event stream so external clients can build accessible views without scraping terminal output.

2. **Ship a line-oriented “assistive terminal mode,” not merely a color theme.** In this mode, avoid full-screen redraws, spinners, Braille animation, and cursor-position tricks. Emit stable headings, labels, bounded progress updates, explicit error text, and an end-of-task summary. Keep color optional and never make it the only signal. Provide predictable keyboard commands for pause, cancel, inspect, approve, and move focus out of a prompt. This follows the documented GitHub CLI findings and WCAG2ICT’s treatment of text applications. [2] [4]

3. **Make the dashboard keyboard- and screen-reader-first.** Use native controls and visible text labels; give every interactive element an accessible name and, where needed, a concise description. Implement landmarks, a visible and non-obscured focus indicator, keyboard escape paths, and status/live-region semantics for progress and errors. Keep task output in a navigable log with headings and filters rather than a canvas-only transcript. W3C specifically notes that names distinguish controls and convey their purpose, and that status messages should be announced without stealing focus. [3] [10]

4. **Make task continuity a first-class surface feature.** Persist a resumable task timeline and expose the same “where it is / what it needs / what changed / what can I do next?” view in CLI, TUI, API, and dashboard. Let users choose notification policy (silent, summary, spoken-friendly, webhook) and replay missed events. Use a stable run ID and idempotent action IDs so a user can approve or cancel from another surface without duplicate execution. This is a product recommendation, not a claim that a particular implementation has been experimentally validated.

5. **Separate proposal, approval, and execution with a trust ledger.** Show the exact tool, target, parameters, data sources, requested capability, expected side effect, and risk level before approval. Record who approved what, when, from which surface, and the resulting tool output. Enforce authorization in a policy/execution component outside the model; bind approval to the exact normalized call and expire or consume it atomically. Unknown tools and changed parameters should fail closed. This directly operationalizes OWASP’s documented guidance. [5] [6]

6. **Treat the sandbox as a measurable capability profile.** Offer profiles such as read-only workspace, network-denied build, allowlisted-egress research, and isolated disposable VM for untrusted code. Run as non-root, minimize Linux capabilities, avoid host filesystem and socket mounts, apply seccomp/AppArmor/SELinux where available, cap CPU/memory/disk/processes, and put credentials behind a scoped broker rather than environment variables. Display the effective profile in every surface and make “approval granted” visibly distinct from “OS isolation verified.” Docker and NIST guidance support this defense-in-depth framing; neither implies that an arbitrary container is an absolute boundary. [7] [8]

7. **Create an interview-safe capability boundary.** Support a mock-interview skill that asks questions, waits for the user’s answer, and gives coaching, accessibility-oriented practice, and post-session feedback. Support disclosed assistance that is user-controlled and employer-compatible: transcription, speech output, captioning, accessible prompts, extra time, and user-authored notes, with local processing and no recording by default where feasible. Do not ship covert live answer-feeding that listens to an interviewer and whispers generated answers as if they were the candidate’s own response. It risks misrepresentation, violates the integrity expectations of many hiring processes, may expose interviewer/employer confidential information, and can create sensitive audio/transcript retention risks. The safer APEX design is to make accommodation mode explicit, configurable, inspectable, and easy to disclose—not to decide that a disability justifies impersonation. DOJ guidance supports accessible accommodation and transparency around hiring technology, while making no claim that covert assistance is permissible. [9]

8. **Test accessibility as a compatibility contract.** Maintain manual test paths with at least a screen reader, keyboard-only navigation, high contrast, reduced motion, and terminal text review; add automated checks for names, focus, live regions, contrast, keyboard traps, and status-event completeness. Test the same scenario through each surface and compare event IDs, permissions, and resulting state. Invite blind and low-vision developers to review real workflows, not only static screens. The research evidence is small (12 developers in [1]), so use it to identify failure modes and test needs, not to claim population-wide effectiveness.

## Cautions and boundaries

- **UI approval is not isolation.** A confirmation button proves that someone saw and accepted a rendered proposal. It does not prevent prompt injection, confused-deputy behavior, replay, data exfiltration, or a compromised tool from acting outside its intended scope. Policy enforcement, exact-call authorization, logging, and OS/runtime controls must remain effective if the dashboard is bypassed.
- **Accessibility is not a single “accessible mode.”** Screen-reader users, low-vision users, motor-impaired users, people with cognitive disabilities, and users of different terminals can need conflicting presentation choices. Prefer user-selectable verbosity, motion, color, notification, and density settings over one persona toggle.
- **Do not treat a local model as automatically private.** Connectors, telemetry, logs, memory, model APIs, browser content, and interview audio can all expand the data boundary. Make retention, redaction, export, deletion, and network destinations visible and configurable.
- **Do not imply market prevalence or broad efficacy.** The cited CLI study is exploratory and small; the designs above are hypotheses grounded in standards and documented failure modes. Validate with task-based accessibility testing and threat modeling before making performance or inclusion claims.
