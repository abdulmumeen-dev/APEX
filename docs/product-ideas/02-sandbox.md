# APEX product opportunity: secure sandboxing for autonomous CLI agents

## User problem

An autonomous CLI agent is useful precisely because it can read files, run commands, install dependencies, call connectors, and persist work. Those same powers create a high-impact failure mode: untrusted repository content, web pages, dependency metadata, plugin output, or a malicious prompt can redirect the model into tool misuse, data exfiltration, destructive edits, credential theft, runaway compute, or a sandbox escape. APEX users need a self-hostable default that lets an agent work unattended inside a bounded workspace without confusing a visible approval prompt with a real security boundary.

The problem is compounded by APEX’s one shared runtime and multiple front ends. A policy applied only in the CLI can be bypassed by the daemon, API, dashboard, plugin, or delegated agent. Users also need a way to bring their own model provider without granting that provider—or model-generated code—ambient host credentials.

## What is documented evidence

1. **Prompt injection and excessive privilege are agent-specific risks.** OWASP lists direct and indirect prompt injection, tool abuse and privilege escalation, data exfiltration, memory poisoning, excessive autonomy, denial-of-wallet, supply-chain attacks, and cascading multi-agent failures as key risks. It recommends per-tool scoping, external authorization middleware, untrusted-input treatment, isolated memory, bounded recursion/cost, and adversarial regression tests. [1]

2. **Approval UX is not containment.** OpenAI’s Codex documentation explicitly separates the two controls: the sandbox determines technically which files and network resources commands can access; the approval policy determines when the agent pauses. Its dangerous full-access mode removes both controls. [2] [3] Anthropic reports that users approved roughly 93% of Claude Code permission prompts in its telemetry and describes approval fatigue as a reason to cap what the agent is able to do rather than relying on supervision alone. This is vendor telemetry, not a general prevalence estimate. [4]

3. **Real agent tools have had boundary and validator failures.** NCC Group’s independent coding-agent review groups observed issues into sandbox escape, permission-prompt bypass, and sensitive-file overwrite. It describes symlink/path-canonicalization problems, hooks and configuration files that cross the boundary, and command-validation/parser differentials in which a supposedly safe command can gain write or execute behavior. [5]

4. **A useful sandbox needs both filesystem and network controls.** Anthropic’s October 20, 2025 engineering write-up says filesystem isolation prevents modification of sensitive files, while network isolation prevents exfiltration or malware downloads; it argues that either one alone is insufficient. Its implementation uses OS-level primitives (Linux bubblewrap or macOS seatbelt), a proxy for domain policy, and applies restrictions to subprocesses as well as the direct tool. [6]

5. **Container hardening is defense in depth, not a universal host boundary.** Docker documents seccomp as a kernel feature that restricts container actions and says its default profile blocks around 44 of 300+ system calls. [7] NIST SP 800-190 (September 2017) recommends grouping containers by sensitivity and threat posture, warns that runtime compromise can affect containers and the host, and recommends mandatory access controls, signed/vetted images, vulnerability scanning, resource/runtime controls, network segmentation, and least privilege. [8] OWASP’s Docker guidance notes that rootless mode reduces the impact of daemon/runtime compromise but does not guarantee protection from kernel vulnerabilities because the kernel remains shared. [9]

6. **Interview assistance has an integrity and accessibility split.** The U.S. Department of Justice guidance on AI hiring (May 12, 2022) says employers must provide reasonable accommodations during hiring and gives examples such as assistive equipment, policy changes, and accessible interview software; it also warns that hiring technology can screen out disabled applicants and recommends telling applicants how technology is used and evaluated. [10] JAN’s practical hiring guide gives concrete examples such as screen-reader-compatible interviews, written questions, and extra assessment time, and recommends minimizing confidential medical information. [11] These sources support mock coaching and disclosed assistive workflows, not covert answer-feeding that misrepresents a candidate’s unaided performance. A real-time covert answer agent can expose interview audio, personal data, and employer-confidential material to a model/provider while undermining informed consent and assessment integrity; APEX should not optimize or market that behavior.

## Actionable APEX product designs

1. **One policy-enforced execution broker for every surface.** Route CLI/TUI, API/daemon, dashboard, plugins, connectors, skills, and delegated agents through a single broker. The broker should resolve an immutable action request (actor, session, tool, exact argv/arguments, paths, network destinations, credential class, risk tier), enforce policy, and execute only through the sandbox. Never trust a model-supplied `user_confirmed` flag; bind approval to the exact request, actor, expiry, and one-time nonce, then consume it atomically.

2. **Layered local isolation with an explicit strength ladder.** Make the default a disposable workspace with OS-enforced filesystem and network isolation, no host home-directory bind mount, no ambient secrets, non-root identity, dropped capabilities, `no-new-privileges`, seccomp, AppArmor/SELinux where available, PID/process/file-descriptor/memory/CPU/time limits, and default-deny egress through a proxy. Offer stronger profiles using a microVM or remote isolated worker for hostile code, untrusted plugins, browser automation, or multi-tenant use. Label a plain container as “shared-kernel containment,” not “strong isolation.”

3. **Capability-scoped connectors and secret brokerage.** Keep API keys, SSH keys, signing keys, cloud metadata, and host credentials outside the sandbox. Expose narrow broker operations—such as “fetch this repository,” “open this pull request,” or “upload this artifact”—that validate destination, branch, method, size, and data classification. Inject short-lived, audience-bound tokens only into the broker, not the agent environment. Default network to off; allow explicit domain/method/byte/time budgets and block raw POST exfiltration unless a policy specifically permits it.

4. **Safe workspace semantics that survive adversarial paths.** Canonicalize paths before authorization; reject symlink, hard-link, mount, archive-slip, case-folding, Unicode, and Windows path ambiguities; protect `.git`, hooks, agent configuration, secrets, and policy files; keep the policy/executor outside the writable workspace. Treat package scripts, Makefiles, Git hooks, IDE metadata, README instructions, issue text, and plugin output as untrusted data. Add regression fixtures for every bypass and run them in CI whenever a model, tool, parser, sandbox, or policy changes.

5. **Network and data-flow guardrails, not just command allowlists.** Prefer structured tool calls over free-form shell. Inspect and classify outbound requests, redact secrets/PII, cap response size, and record the destination, method, bytes, and initiating action. Use separate read-only and write-capable tools. An approval should show the normalized command plus affected paths, network destinations, credential scope, and predicted side effects—not merely the model’s prose explanation.

6. **Auditable session receipts and a kill switch.** Record tamper-evident events for prompt/input provenance, policy decision, sandbox profile, model/provider, tool request, approval/denial, process tree, filesystem diff, network decision, connector use, and cost/loop counters. Provide `apex stop`, API revocation, process-tree kill, credential revocation, and workspace snapshot/rollback. Redact sensitive content by default and make retention configurable for self-hosters.

7. **Risk-adaptive autonomy with bounded delegation.** Use low-risk profiles for read-only analysis and tests, medium-risk profiles for workspace writes, and high-risk profiles for external side effects, production access, financial actions, or persistent automations. Delegated agents inherit a strictly smaller capability set and cannot grant themselves permissions. Enforce depth, wall-clock, token, retry, tool-call, storage, and spend budgets, with circuit breakers on repeated denials or anomalous egress.

8. **Interview-beneficial modes, not covert answer feeding.** Ship a mock-interview mode that generates questions, gives delayed hints, scores reasoning, and produces a study plan; a disclosed accessibility mode that supports captions, transcription, text-to-speech, extra time, written prompts, or an employer-approved assistive workflow; and a post-interview debrief that helps the user reflect. Require an explicit “this is an assessment; external assistance is permitted” declaration before any live-assistance feature, and otherwise disable live answer generation, hidden overlays, earpiece scripts, or impersonation. Keep interview audio local or ephemeral by default, show recording/transcription state, obtain consent where required, and provide deletion/export controls.

## Cautions and decision gates

- Do not claim that a container, seccomp profile, permission prompt, or model guardrail makes arbitrary code safe. The shared kernel, runtime, host configuration, mounted paths, plugins, and broker remain part of the threat model.
- Do not provide a “YOLO” mode that silently removes both sandbox and approval controls. If an expert explicitly chooses full host access, make it conspicuous, require an out-of-band policy change, and log the decision; it is not a security feature.
- Do not put secrets in environment variables or mounted files merely because the agent is in a container. Use a broker with short-lived, scoped credentials and test exfiltration paths.
- Self-hosting shifts operational responsibility to the user. APEX should ship a threat-model checklist, secure-default diagnostics, sandbox self-tests, image/signature/update guidance, and platform capability detection with fail-closed behavior when required isolation is unavailable.
- The design recommendations are not evidence of market size or measured effectiveness. Anthropic’s prompt-reduction and approval figures are internal vendor reports; NCC Group’s findings document classes of vulnerabilities, not a prevalence estimate. Interview integrity, privacy, employment-law, and accommodation requirements vary by jurisdiction and employer policy; APEX should encourage disclosure and professional/legal review rather than deciding eligibility itself.
