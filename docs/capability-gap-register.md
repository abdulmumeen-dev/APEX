# APEX capability-gap register

This register answers the practical question, “What is APEX still missing?” It separates current implementation from product goals so the desktop build does not get mistaken for feature parity. Research about other products informs the gaps; it does not prove that APEX already implements them. See the [product roadmap](roadmap.md), [desktop-agent review](desktop-agent-review.md), and [provider compatibility review](cloud-provider-compatibility-review.md).

## What the first desktop release will and will not mean

A downloadable Electron app plus the local runtime solves part of the *delivery and local-control* gap: the source now launches a desktop shell, lets the user select a workspace, configure Ollama or a compatible API, run tasks, inspect traces, and approve file writes without signing into an APEX cloud service. The Linux AppImage has been smoke-opened under Xvfb through its chooser/window path, but is not tested on a real user machine or publicly released. The interface now lists **Create Game** and **Create Video** as planned sections; they do not create games or videos yet. The desktop also does **not** yet deliver browser/computer control, secure arbitrary code execution, broad app integrations, durable automations, or parity with Manus, Kimi, Hermes, OpenClaw, Meta Muse, OpenAI Dots, or Grok. Those remain separate engineering outcomes.

A selected cloud model still needs internet and receives request data according to the user's chosen provider. An offline claim applies only when all required app assets and models are installed and the selected local tools do not require the internet.
